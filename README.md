# U345

Exam results and course ratings for every Chalmers course: pass rate, grades, every exam date on record, what students thought of the course, and a course planner where you fill a year of a programme with courses and see those numbers for each.

Exam results come from the public [stats.ftek.se API](https://github.com/Fysikteknologsektionen/chalmers-course-stats/blob/main/API.md). Course ratings come from [Chalmers course surveys](https://www.chalmers.se/en/education/your-studies/plan-and-conduct-your-studies/course-evaluation/), over the last three academic years. Study periods, rules and choices come from the [programme plans on chalmers.se](https://www.chalmers.se/en/education/your-studies/find-course-and-programme-syllabi/programme-overview/). The site is static, apart from one Vercel Function that draws the link preview image of each course.

GitHub Actions fetch the sources and commit them to `data/`:

- `data/results.json`: a nightly Action runs `pnpm fetch-results` and commits when results change, a few times per study period.
- `data/evaluations.json`: a monthly Action runs `pnpm evaluations`. The survey site is slow to crawl and changes rarely.
- `data/programme-plans.json`: a weekly Action runs `pnpm programme-plans` and commits when a plan changes. It holds every academic year since 2021/2022. The current one switches in July.
- `data/names.json`: the same Action writes the English and Swedish names of every course and programme on chalmers.se since 2021/2022, and the newest academic year chalmers.se offers each course in.

Every push deploys to Vercel. The build turns `data/` into static JSON next to the site and reads no network, so it works while a source is down. When a fetch fails, the committed data stays as it was.

## Run locally

```sh
pnpm install
pnpm snapshot
pnpm dev
```

`pnpm snapshot` takes a few seconds and writes about 20 MB to `public/data`.

## Architecture

Data flows one way, from the sources to the pages:

```
stats.ftek.se, course surveys, chalmers.se, Chalmers' eligibility guide
  → scripts/fetch-results.ts, evaluations.ts, programme-plans.ts, eligibility.ts
  → data/*.json (committed)
  → scripts/snapshot.ts, which calls buildSnapshot in scripts/build-snapshot.ts
  → public/data (index.json, courses/<code>.json, plans/<start>.json, eligibility.json)
  → the app (src/data/queries.ts), api/og.tsx and scripts/page-meta-plugin.ts
```

Each fetch script is the only code that knows its source. It exports its pure transforms, which the tests run on recorded responses in `scripts/fixtures`. Its `main` runs only when the script is started directly. `buildSnapshot` joins the six data files and does no I/O, so its test covers every join.

### Modules

These files are in `src/domain` unless the path says otherwise.

- `snapshot.ts` holds the schemas of `public/data`. The build writes files in that shape, and every reader parses them with these schemas.
- Each data file has its schema in the module of its source: `course-stats.ts` for results, `evaluation.ts` for surveys, `programme-plans.ts` for plans, `names.ts` for names and `eligibility.ts` for the eligibility guide.
- `grades.ts` and `spread.ts` hold the grade and distribution maths. `names.ts` also holds name matching.
- `catalog.ts` turns the snapshot into the course list: search, scopes and sorting, for courses with and without results.
- `programme-plans.ts` places courses in plans and builds one year of a programme with `planYear`. `degree.ts` holds degree requirements and progress. `eligibility.ts` checks the first three years of a plan against what Chalmers' eligibility guide asks for admission to a master's programme. `planner.ts` holds the candidates, clashes and `yearView`, which is everything a year of the planner shows.
- `planner-state.ts` holds the planner's state: what the URL and the device memory say together (`resolvePlanner`), and what each action changes in both (`plannerStep`). `src/features/planner/use-planner.ts` is the only code that applies those changes.
- `src/features/<page>` renders a page from those functions. `src/components` holds what several pages share, and `src/components/ui` is generated by shadcn.

### Where a change goes

- To add a field from a plan or a course syllabus, read it in `toCourses` in `scripts/programme-plans.ts` and test it on the fixtures. Then add it to `planCourseSchema` in `src/domain/programme-plans.ts`.
- To add a degree rule, change `src/domain/degree.ts` and its test. The planner shows what `yearView` returns.
- To add planner state, add a field to `resolvePlanner`, an action to `plannerStep` and a search param to `plannerSearchSchema`, all in `src/domain/planner-state.ts`. Test the field and the action.
- To add a survey question, add it to `QUESTIONS` in `src/domain/evaluation.ts` and to `QUESTION_TEXT` in `scripts/evaluation-pages.ts`, and add its words to both i18n files.
- To add a UI word, add it to `src/lib/i18n/en.ts`, then to `sv.ts`. The type checker finds a missing translation.
- To add a data source, write a script under `scripts/` that writes a file to `data/`, a schema for the file in `src/domain`, an input to `buildSnapshot` and a workflow in `.github/workflows`.
- To read a new phrasing of the eligibility guide, add its pattern to `scripts/eligibility.ts`. Test it in `scripts/eligibility.test.ts` on the recorded guide in `scripts/fixtures`.
- To fix a typo in the eligibility guide, add a correction to `data/eligibility-corrections.json` and run `pnpm eligibility`.
